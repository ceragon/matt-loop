# 中途本地 IO 失败的交付：io_failed 顶层兜底

## 背景

#87（spec 定案 #111，grill 八题裁定 Q1–Q8 全部接受）：调用方放行一轮后，分发脚本在
台账已开、终态未到的中途遭遇本地磁盘 IO 失败（磁盘满、权限变更、目录被清理）时，
`OSError` 不是 `DispatchError`，会冒出整轮：打 traceback、退出码 1，没有结果文件、
没有通知记录、不发 webhook。传话助手什么都收不到——本轮彻底失明，无法区分「还在跑」
与「已死」；而放行 id 可能已消耗、目标会话可能已收到提示词正在工作。台账记过程、
不是交付，救不了这个场景。ADR-0022 决定 3 把这个洞如实保留、转独立 issue 登记；
本 ADR 是该 issue 的定案。

同形盲区不止台账：回读原料/本轮原料/干净回复全文落盘、runs 目录创建、api 抽取读
本轮原料等中途本地 IO 点有一模一样的洞。

## 决定

（#87 grill 裁定、#111 spec 定案；外部契约新增一个 error kind，成功路径与既有
error 路径行为逐字不变。）

1. **整类范围、兜底只有一处**：堵整类中途本地 IO `OSError`——runs 目录创建、台账
   open＋全部中途台账写、回读原料/本轮原料/干净回复全文落盘、api 后端读本轮原料。
   分发脚本主入口（将来管线 run）顶层新增 `except OSError` 兜底，转成
   `DispatchError("io_failed", …)`，走与既有 `except DispatchError` 完全相同的
   error 出口。未来新增的写点自动被覆盖，不再逐点补漏。
2. **有现成语义的读取点逐点包既有 kind**：发送前 sha 复核读提示词失败→
   `prompt_unreadable`；抽取提示词读失败→`missing_prompt`。不新增同义 kind、
   不膨胀契约面；其余归 `io_failed`。
3. **单一通用 kind、退出码恒 1**：`io_failed` 不按产物拆（调用方动作相同：修本机
   环境；kind 表按动作分列）；命名风格对齐既有 `hc_failed`/`app_failed`/
   `launch_failed`。环境故障不是静态旗标错，不进退出码 2 的「补参同 id 重试」家族。
4. **message 与两态 hints**：message 带操作（异常类名）＋路径＋`OSError` 原文
   （运行时载荷带本机路径是既有口径，仓库产物仍守隐私红线）。hints 按「台账是否
   已开」（首版台账成功落盘）机械分两态：未开（目录创建/首写失败）→放行 id 未消耗、
   环境修复后同放行 id 重试；已开→id 已消耗、部分状态如实带出、修复后新放行 id
   （同 id 重试撞 `duplicate_release`）。与 `adopt_failed` 创建路径/预检路径同 kind
   分动作的先例同构。
5. **交付完全复用既有 error 路径**：尽力写终态台账（`error:<kind>`＋`failed_at`，
   失败吞）、`emit_result` 既有降级（`notify_record_error`／stderr 诊断／webhook
   照尝试／stdout 照输出）。不重试、不做内存缓冲补写、不造第二套交付通道；与
   `emit_result`「唤醒优先、写失败不改退出码不递归」口径对齐。磁盘满/只读时快速
   失败返回，不挂起等待一个不会好转的环境。
6. **原子写函数与 Journal 设计零改动**：`write_json_atomic` 原样不动（仍抛
   `OSError`）；ADR-0022 的 `phase`/`fact`「`OSError` 原样冒出」不被推翻——照冒至
   run 顶层、由顶层映射。journal 重构切片继承修后行为、零冲突。
7. **`duplicate_release` 仍是第一闸**：`io_failed` 绝不抢占它；原子写失败残留的
   tmp 文件不阻塞重试（duplicate 闸只看台账/回读原料存在）。
8. **文档同步、GLOSSARY 零改动**：REFERENCE.md error kind 表＋error 返回契约段
   更新；ADR-0022 决定 3 加补记指向本 ADR；`io_failed` 是代码名、不进词表
   （ADR-0016 决定 13 口径）。

## 与既有 ADR 的关系

- **ADR-0022**：决定 3「台账中途写失败是外部契约上的洞，另开独立 issue」由本 ADR
  关闭，决定 3 已加补记；`Journal` 设计与「行为冻结」措辞不变，journal 切片继承
  修后行为。
- **ADR-0021**：本票是行为性 bugfix、不是重构片，不进串行队列（开工时无改 dispatch
  的在途切片）；按决定 5，S 合入前合入的 bugfix 自然进入快照基线。文档＋代码＋测试
  同一实施 PR 交付，同刻生效，不留说谎窗口。
- **ADR-0014**：通知投影与通知记录契约不动，只复用（error 通知不套成功白名单、
  唤醒优先）。
- **ADR-0020**：将来管线 run 抽出时，顶层兜底随 main 体搬入，口径不变。

## Considered Options

- **写入函数内转换 `OSError`**：否——会波及 `Journal.fail` 的吞异常语义，且非台账
  写点仍需第二套兜底；顶层一处映射覆盖整类。
- **按产物拆 kind**（台账写失败/回复落盘失败各一个）：否——调用方动作相同（修本机
  环境），拆只膨胀契约面；kind 表按动作分列。
- **退出码 2**：否——环境故障不是静态旗标错，混进「补参同 id 重试」家族会误导调用方。
- **重试／内存缓冲补写**：否——磁盘满/只读不会好转，挂起等待只延迟失败；唤醒优先
  要求尽快把结构化 error 交付出去。
- **等 journal 重构切片顺手修**：否——地图硬约束 1：契约改动不在重构图里解决，转
  独立 issue；现在修，修法随重构自然存活。
- **新增 GLOSSARY 词条**：否——`io_failed` 是代码名，词表只承载领域语义。

## Consequences

- 调用方在磁盘故障下仍收到一行结构化 error JSON 与 webhook 唤醒，不再失明；处置
  路由到「修本机环境」而不是「去目标屏幕前查看」。IO 失败只停本轮，不杀不重发
  目标会话，已放行的提示词不被静默重发。
- 代价：error kind 表多一行；两态 hints 依赖「首版台账成功落盘」的机械旗标。
- error 出口自身的终态台账写仍吞 `OSError`——`io_failed` 的终态写可能静默失败，
  这是尽力而为口径，不是新洞。
- 隐私：message 运行时带本机路径（既有口径）；本 ADR 与测试样例遵守公开仓库红线。
