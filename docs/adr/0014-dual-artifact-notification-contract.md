# 双产物通知契约：全量结果＋通知投影/通知记录，唤醒优先

> 补记（ADR-0019，#79）：决定 2 成功白名单由 11 字段增补为 13（加 `complete`/
> `complete_reason`），成功通知恒带完整性标记；其余契约不变。详见 ADR-0019。

## 背景

issue #52：调用方（Grok Bot）的例行任务是所有 webhook 唤醒的落点，按周配额实测约占
3.5%。单条通知的成本与它承载的信息量不成比例——多数通知是「无需选择的完成结果」或
同一放行的重复通知，按例程只需一句话交回；但每次唤醒都要起一整轮 agent，把约 777 字
的例程全量载进上下文，再分类、核对台账、判读改写标记。

优化对象是**单次唤醒成本**（模型、上下文、核验动作与输出），不是减少唤醒次数：正常
成功、需要用户拍板和 error 都仍有各自的交付路径，减少通知或取消纯成功交回不是手段。
现有记录没有逐次 token/模型/工具调用/完整耗时，不能把成本百分比拆给固定提示、历史
上下文、通知载荷、核验或输出，也不能用字节数冒充 token。

同时有三项结构性问题：

1. 全量结果同时承担审计与唤醒职责，且实际 POST 出去的通知正文没有独立的本地逐字记录。
2. 旧例程包含云端传话助手做不到的本机台账/原文核验，并混入独立的 dev-loop 分类与回写职责。
3. dev-loop 另维护门铃、watcher、模型注册表、启动 adapter、会话管理和答案传输，与 loop
   的运行、通知、放行及会话能力重复。

本 ADR 只裁定**阶段一**的仓库侧双产物与跨调用方通知契约（问题 1）；dev-loop 收敛为
Linear 适配器（问题 3）与例程切流（问题 2 的部署）属阶段二，另在 dev-loop 形成 ADR。

## 决定

1. **双产物分职**：`<放行id>.result.json` 保持**全量结果**，既有字段语义不变，仍是审计与
   回看对象、事实源；stdout 与全量结果的既有一致关系不变。新增 `<放行id>.notify.json`
   同时承担**通知投影**（供传话助手判读与交回的唤醒载荷）与**通知记录**（实际 POST 正文
   的本地逐字记录）两职。
2. **成功白名单**：成功通知（`ok=true`）严格只含 11 个判读/交回字段，顺序固定：
   `ok`、`release_id`、`target`、`needs_user`、`questions`、`conclusion`、`blocked`、
   `rewritten`、`run_record`、`elapsed_s`、`next_skill`。投影从本轮结果逐字选取，不补造、
   不改写；结果缺某字段则不带（生产路径恒齐全）。
3. **error 全量**：error 通知不套成功白名单，保留发送前完整 error 对象及其诊断、部分状态
   和 `message/hints`，补参/授权/重试/部分状态判断不因省字节而丢失。
4. **发送诊断只归全量结果**：`webhook`、`webhook_error`、`webhook_error_detail` 是 POST
   完成后才产生的发送诊断，只记全量结果，绝不进通知投影/通知记录。
5. **字节一致**：通知投影只序列化一次；通知记录文件内容与实际请求体字节完全相同，不为
   文本文件惯例额外追加换行。主出口、代理重试与直连兜底全部复用同一组序列化字节（仍可按
   现有代理要求为每次尝试创建新的请求对象）。
6. **落盘与发送顺序**：构造通知对象 → 只序列化一次 → 写入通知记录 → 首次 POST → 必要重试
   → 写入全量结果并输出 stdout。无论 webhook 是否启用，只要已建立安全的运行路径，就生成
   相同的通知投影与通知记录。
7. **唤醒优先（写失败降级）**：通知记录写失败时仍尝试 POST，并在 stderr 与全量结果诊断
   （`notify_record_error`，异常类名）中明确记录；若全量结果也不可写，至少 stderr 与 stdout
   不得声称记录完整。通知记录写失败**不改变一轮的退出码或 `ok`，不递归生成第二条 error
   通知**——审计故障不变成结果丢失，故障域保持清晰。
8. **早期 error 路径安全**：对非法放行 id 等尚未建立安全运行路径的早期 error，保留现有
   error 输出与发送行为，不用非法 id 构造文件名，也不虚构通知记录已经存在。
9. **统一调用方读取契约**：DS Bot 与 Grok Bot 都**优先读取 `notify.json`**，只有需要完整
   诊断、审计或回看时才读取 `result.json`。云端传话助手实际只能直接取得 webhook 正文；
   `notify.json` 是发送端通知记录，不是云端可读本机文件。`run_record` 在成功通知中仅是
   提供给用户的记录位置，传话助手不得尝试读取。
10. **部署形状不膨胀**：webhook 的 `off/sent/failed`、重试次数、代理和脱敏错误诊断语义保持
    现状（ADR-0003）；不新增 `LOOP_WEBHOOK_*` 或其他环境变量开关。

## Considered Options

- **维持单产物（全量结果既审计又唤醒）**：审计字段演进迫使每次唤醒载入全部诊断，且 POST
  正文无独立逐字记录，否。
- **按 `needs_user` 过滤纯成功通知以减少唤醒**：把优化目标误读为减少唤醒次数，会丢正常
  完成交回，否（Out of Scope）。
- **error 也套成功白名单**：补参/授权/重试/部分状态判断丢诊断，否。
- **通知记录写失败即整轮 error**：审计故障升级为结果丢失，违背「发失败不连累整轮」哲学，否；
  选唤醒优先＋降级诊断。
- **通知记录写失败递归发第二条 error 通知**：故障域放大、可能风暴，否。
- **为文本文件惯例给 notify.json 追加换行**：破坏「文件字节＝请求体字节」的排障保证，否。
- **新增 webhook 环境开关/兼容 profile 控制投影**：部署形状膨胀，否（Out of Scope）。
- **云端传话助手读取发送端 notify.json/run_record**：云端取不到本机文件，且制造「已核验
  本机原文」假象，否；通知记录只供发送端审计排障。

## Consequences

- 成功唤醒只载入 11 字段投影，审计字段演进不再连累每次唤醒；error 诊断完整保留。
- 排障可证明当时发送了什么（通知记录逐字），重试不会生成语义或字节不同的通知。
- 通知记录写失败不丢结果、不放大故障；早期 error 不制造路径安全问题。
- DS Bot/Grok Bot 共享同一窄入口（先 notify 后 result），契约成文于 SKILL.md/REFERENCE.md。
- 词汇表以「调用方」「传话助手」「通知投影」「通知记录」「Linear 适配器」「单次唤醒成本」
  为正式词汇（本批 GLOSSARY 修订）。
- 传话例程定稿（357 非空白字，较原 719 字降 50.3%）成稿于 `docs/relay-routine.md`，
  **已审核未切流**；阶段二专用测试票通过并经用户批准后才替换线上旧例程。
- 成本验收只看自然唤醒前后对照（纯成功/needs_user/error 三类各 ≥20 次，中位单次消耗纯成功
  与 needs_user 均须降 ≥20%，error 单独报告），安全项一票否决；阶段一不以最终 20% 目标提前收口。
- 与 ADR-0003（webhook 跟随系统代理）一致：出网/重试/脱敏矩阵不变，只改 POST 正文为投影字节。
  与 ADR-0002（脚本干机械活）一致：投影/落盘/发送顺序是新增确定性机械步，仍归脚本。
