# 一个开 bash 的 pi（信使）全包发送、等待与取回

> **Superseded by [ADR-0002](0002-script-does-mechanics-pi-does-extraction.md)**（2026-11-19 16:40 用户撤销 B、改回 C：脚本干机械活，pi 干提炼）。以下原文保留作历史，不再有效。

一轮之内，把已放行的提示词发进目标会话、等它落定、取回最新回复，全部交给同一个开 bash 的无头 pi（信使）；六条发送安全写进信使提示词的硬约束，不拆成「脚本发送与等待、pi 只提取」。这是用户在制图拷问中的裁定（Q2），裁定时没有留下进一步的理由。

## Considered Options

- **A 两个 pi**：开 bash 的 pi 负责发送与轮询，靠提示词白名单约束；不开工具的 pi 负责提取。
- **B 一个开 bash 的 pi 全包**（采用）。
- **C 脚本发送与等待，pi 只提取**：脚本用 `hc` 发送与等待（纯代码），pi 加 `--no-tools` 只做提取，屏幕文本由脚本喂给它。制图时推荐过 C，理由是「原文照发、只发一次、不 `--force`、不替对方答」可以由代码保证，而 A、B 里 pi 每轮询一次都要走几次模型推理。用户选了 B。

## 为什么记成 ADR

三个条件都满足：

- **难回头**：信使提示词、外层脚本、skill、烟测都围绕它写。
- **不看上下文会奇怪**：为什么让一个很慢的本地模型带着 bash，去做「只发一次」这种安全敏感的事，还只靠提示词约束。
- **有真实取舍**：上面的 A / B / C，推荐方案与采用方案不同。

## Consequences

- 六条发送安全只是提示层约束，不是机械保证：pi 执行工具前不会询问，bash 能写任何文件，也能调用任何命令。
- 研究确认了 B 的具体风险：bash 超时或非零退出只会作为工具错误回给模型，模型可能重发 `hc send`；pi 没有整轮总超时；`--mode json` 下模型失败时退出码仍为 0；bash 继承完整的父进程环境，密钥放进 pi 的环境会被模型读到。
- 因此需要由外层脚本做确定性兜底，但不接手发送、等待与取回。兜底做到哪里，由「外层脚本的职责边界」一票裁定。
- 若兜底仍不足以守住六条，退路是 C。
